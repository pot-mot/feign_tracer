# 2026-10-26

## feign-tracer 内存优化：P1 + P2 落地

在上一轮 P0（SLL + token 复用 + 二分扫描）基础上继续，工作区改动未提交。

### 新增模块
- `src/store/bodies.ts`：方法体工作库。解析完一个文件就把 `MethodInfo.calls/locals`
  按 `method_id` 存成一行 JSON（`calls_json`/`locals_json`），随后 `delete` 掉内存字段；
  读取侧 2048 条 LRU。工作库是临时文件，`close()` 时删除。
  `detachBodies()` 负责「落库 + 剥离 + 统计」，`store` 省略时只统计不剥离（对照路径）。
- `src/store/tree-spool.ts`：调用树 NDJSON 暂存。逐端点展开后立即 `sink.write` 并清空
  `children`，写库时 `readTreeSpool` 流式读回。序列化用 replacer 丢掉 `children`。

### 主要改造
- `model.ts`：`MethodInfo.calls/locals` 改为可选；`AnalyzeOptions.workDb` 新增（默认 true）。
- `graph/index.ts`：新增 `callsOf` / `localsOf` / `fieldTypesOf`（后两者记忆化 → 去掉
  `collectFields` 的 O(methods × supers) 重算）。
- `graph/resolve.ts`：不再直接读 `method.calls/locals`。
- `graph/files.ts`：`buildFileAnalyses` → `analyzeFiles`，一次遍历同时产出 files 与
  `totalCalls`/`resolvedCalls`（原来 `countResolvedCalls` 会把所有方法再解析一遍）。
- `graph/calls.ts`：新增 `CallTreeSink` + `drainTree`；跨根解析缓存加 4096 上限。
- `parse-pool.ts`：静态分批 → **逐文件动态派发**（worker 完成一个领一个）；
  `onFile` 回调 + `delivered` 位图保证每个下标只交付一次；worker 失败只补跑未交付文件。
- `analyze.ts`：`ParseAccumulator` 按任务下标累积，`acceptOutcome` 逐文件蒸馏。
- `sqlite.ts`：`treeSpool` 选项；`insertCallTree` 拆出 `insertCallNode` 供两条路径共用；
  `journal_mode=OFF`、`temp_store=FILE`；去掉 rename 前的 `rmSync`（POSIX/Windows 的
  rename 本身就是原子替换，先删反而有窗口）。
- `common.ts`：SLL 改为**自适应**（连续失败 3 次后关闭），`FEIGN_TRACER_PREDICTION=auto|always|never`。

### 关键发现（P0 的前提不成立）
本仓库 Java20 语法在 `return a.b(x)` 这种最常见写法上 **SLL 必然失败**
（`mismatched input '(' expecting '.'`），根因是 `expressionName`/`ambiguousName`/`pNNA`
的右递归让 SLL 预测选错分支。`examples/shop` 里 `UserController`、`OrderServiceImpl`
都能复现。所以原 P0 等于「每个文件白跑一遍 SLL 再用 LL 重解析」，小文件上 SLL 耗时是
LL 的 5 倍左右。

实测（单文件 880 个调用点）：SLL 1.4s/40 errors，LL 38s、峰值 RSS 227MB（基线 84MB）。
即真正的内存与耗时瓶颈是 ANTLR 的 LL 全上下文预测，不是 ParsedFile 常驻。

后续可选方案（均需改语法并重新生成 parser）：
1. 把限定访问改成左递归 `expression '.' identifier`（标准 Java 语法写法），SLL 可正常解析；
2. 或把 `block` 规则改成「配对花括号浅扫描」，跳过全部语句/表达式解析；但
   `extractLocals` 依赖树里的 `localVariableDeclaration`，需同步改成 token 扫描（groovy 已有先例）。

### 环境备注
本机沙箱的 safe-delete shim 会对删除操作计数并在目标旁生成 `<file>.lock` 空目录；
一旦某 DB 路径被加上 `.lock`，SQLite 打开即报 `database is locked`。
`.tmp/cycles-result.db`、`.tmp/cyc-*.db` 已被污染，`npm run test:cycles` 会因此失败；
换到 `mktemp -d` 下的新路径后 fresh + merge 均正常（已验证）。

## 前后对照测量（同日追加）

样本 `.tmp/perf`：180 文件 / 2640 方法 / 14640 调用 / 1.3MB，`useCache:false`，`--expose-gc`。
用 `git stash` 切回 HEAD（无 P0、无 P1/P2）跑同一脚本。

| 配置 | analyzeMs | writeMs | 峰值 RSS | GC 后常驻堆 |
|---|---:|---:|---:|---:|
| HEAD 基线（8 worker） | 32932 | 163 | 1823MB | 25MB |
| 当前（8 worker） | 31756 | 129 | 1857MB | 24MB |

**结论：时间约 -4%（基本持平），峰值内存无改善。** 本轮 P1/P2 打的是「常驻」维度，
而该样本里方法体总量只有几 MB，敌不过 ANTLR 的解析峰值。

worker 数对峰值是线性关系（当前代码、同一工程）：

| jobs | analyzeMs | 峰值 RSS |
|---:|---:|---:|
| 2 | 99232 | 519MB |
| 4 | 52348 | 945MB |
| 8 | 31756 | 1857MB |

≈ 每个 worker 225MB。所以「400 文件 20G」的构成是 **worker 数 × 单文件 LL 峰值**，
不是 ParsedFile 常驻。可用的即时旋钮：`--jobs`（峰值近似线性）、以及给 worker 设
`resourceLimits` 并在 OOM 时把该文件单独重跑。结构性方案仍是语法层的 SLL 修复。

另：把 `SLL_FAILURE_LIMIT` 从 3 改为 1 —— worker 各自持有状态，8 个 worker 会各白跑 3 次
SLL（每次都重新 lex + parse），改成 1 后 8 worker 的 analyze 从 35441ms 降到 31756ms。
